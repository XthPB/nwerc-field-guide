Cut the search in half · Lesson 68 of 235

Choose the parameter before you split

You’re given item weights and a target, and each item can be used once. Decide whether a subset hits the target exactly. One instance has 42 items with enormous weights. Another has 200 items but a target of only 60,000. The better search depends on which dimension is small.

1. Work one example

Write down the sizes of both candidate computations. Enumerating half of 42 means roughly two million choices per side. For 200 items the same idea explodes, while 60,001 yes/no cells occupy only 938 machine words.

2. What do we need to remember?

If neither capacity nor value is small, split the items and ask what summary you can enumerate for half of them.

3. How do we get the next answer?

Compare target size, item count, number of distinct summaries, and separator width explicitly. A DP over a small range can beat meet-in-the-middle by orders of magnitude. Repeated independent queries can justify preprocessing one half.

Check the boundary. With n=55, “small n” can still mean hundreds of millions of half-sums. Four-way Schroeppel–Shamir enumeration can trade heap work for space by streaming pair sums; it does not make the exponential time disappear.

Cost For quarters of size q≈n/4, sorted pair sums from two quarters can be streamed with O(2ᑫ) heap entries. The full two-stream exact-sum search uses O*(2ⁿᐟ²) time and O*(2ⁿᐟ⁴) space, suppressing polynomial factors.

Try one change

There are 40 items and sums reach a trillion. Why enumerate 20 at a time?

See the reasoning

A target-sized table is huge. Each half has about a million subsets, and a summary such as its sum can join the halves without trying every pair.

From idea to code

  • Meet in the middle for sums
    Keep both lists including the empty subset. For an exact match use equal_range so repeated sums retain their multiplicity. For a closest partner inspect both neighbours of lower_bound.
  • Bitset subset sum
    Set only bit zero at the start. A shifted copy represents taking one item. OR retains the outcomes of skipping it. Choose MAXS large enough for the actual largest queried sum.
