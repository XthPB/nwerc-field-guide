Constructive proofs and implementation · Foundations

A study route from foundations to contest execution

Read with the solution closed

For each problem, read the original statement and solve the samples manually. Spend a real attempt identifying the model and writing a brute force. Open only the first hint when stuck. After seeing the efficient idea, close it and derive the recurrence or invariant yourself.

The five approach stages are a learning ladder. Some are deliberately slow, some are tempting failures, and some are broader extensions. They are labelled so you can learn from them without mistaking every snippet for a passing submission. Full jury C++ sources are provided separately.

A flexible eight-block programme

Block Focus Exit test
1 Modelling, complexity, exact arithmetic, sorting Solve four level-1/2 problems without hints and explain why
2 Greedy proofs, binary search, prefix sums, monotonic queues Produce a proof and a counterexample to a wrong alternative
3 Basic DP, knapsack, strings, state compression Derive state/base/order before looking at code
4 BFS/Dijkstra, SCC, DSU, DAG DP Build the correct graph, including extra state when needed
5 Tree DP/rerooting, range queries, segment trees Implement and differential-test one template of each
6 Bitmask/profile DP, matching/flow, suffix structures Solve at least two level-4 problems with independent reconstruction
7 Probability, interactive, geometry, advanced optimisation State assumptions and guarantees accurately
8 Full contests and targeted repair Complete a timed team simulation and a written postmortem

These are study blocks, not a promise that each takes exactly one week. Move on when the exit test holds. Revisit prerequisites when an advanced chapter feels opaque.

Use a three-pass problem cycle

Attempt: record your model, complexity and where you got stuck. Avoid browsing the solution at the first discomfort.

Reconstruct: after learning the idea, implement from a blank file, run samples and small oracle tests, then submit on an available practice judge if you want full judging. Local samples do not replace hidden tests.

Retain: a few days later, explain the key invariant without notes and solve a related problem. A month later, redo the hardest step or a variant. The library's progress states distinguish reading, attempting, solving and revisiting; a checked box is not mastery by itself.

Build a personal error log

For each miss, classify the cause: wrong model, missing proof condition, complexity underestimate, overflow, indexing, unhandled tie, protocol error, or implementation bug. Write the smallest failing example and the corrected invariant. This is more useful than “need more DP practice.”

A strong postmortem answers: What clue in the statement should have suggested the model? Which brute-force transition was accelerated? What assumption made the optimisation valid? How will I recognise a related problem next time?

Team contest execution

In a five-hour simulation, skim the full set early, assign likely easy solves, and keep a shared list of candidate models and estimated difficulty. Rotate a stuck problem to a teammate with a precise summary of what has been proved. Before coding a difficult solution, do a short proof review together. Before submission, check bounds, integer widths, output format and a few adversarial examples.

Keep a compact reference notebook of implementations you understand. Know whether its use and printing are permitted by the current event rules; check the organiser's current instructions rather than assuming rules from an older year.

What this archive can and cannot predict

The topic explorer counts tags from these 61 guides; tags include meaningful alternatives and overlap. They are learning priorities, not official classifications or probabilities of future appearance. Bitmask encoding, bitset intersections and bitmask DP are different concepts. The broader syllabus deliberately covers important ICPC techniques beyond those used as the main method in this sample.

Your final checkpoint

Pick an unseen level-4 problem. In twenty minutes, write a brute-force model, a candidate efficient state, a complexity calculation and the exact lemma you still need. Even before finishing, that is evidence that you are developing transferable contest reasoning.
