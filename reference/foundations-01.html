Constructive proofs and implementation · Foundations

From a story to an algorithm

You have a list of scoreboards photographed during one match. Goals can only increase a team’s score. Could (2,1) be followed by (1,2)? Use this small decision problem to practice separating the input, the allowed changes and the exact output before choosing an algorithm.

Start with a question you can answer

A scoreboard says (2,1), then (1,2). Can both belong to a game where scores only increase? You do not need to reconstruct every scoring event. One coordinate decreased, so the answer is already no. The useful object is a constraint between consecutive observations.

This is the first contest habit: turn the story into objects, operations, constraints and an objective. “Travel” might mean shortest path, but it might also mean reachability, scheduling, or a deterministic walk. Choose the model before the algorithm.

A five-pass reading routine

  1. Rewrite the output in one sentence: minimise what, count what, or construct what?
  2. Separate guarantees from goals. A connected graph is a promise; a connected chosen subgraph may be your responsibility.
  3. Copy the largest bounds and numeric ranges. Include the sum of sizes over test cases.
  4. Solve a tiny example manually and write down why each decision is legal.
  5. Build a brute-force oracle before optimising an unfamiliar idea.

For n≈20, subsets may be realistic. For n≈2000, quadratic work may fit. For n≈200000, look for near-linear or n log n work. These are starting estimates, not universal timing promises: an O(n²) table of tiny arithmetic is very different from O(n²) allocations or large integer operations.

The cost of a representation

An adjacency matrix uses O(V²) memory even if a graph has only V edges. An adjacency list uses O(V+E). A DP with 200000 × 200000 states is impossible before you even discuss transitions. Always write:

time = number of states × work per state
space = states simultaneously retained × bytes per state

For a subset DP with n=20, 2^n≈10^6; adding a last-vertex dimension multiplies memory by 20. At eight bytes per entry that is roughly 160 MB, before overhead.

C++ that supports reasoning

using ll = long long;
using i128 = __int128_t;
const ll INF = (1LL<<62);
// Cast BEFORE multiplying, not after overflow has happened.
i128 cross = (i128)ax*by - (i128)ay*bx;
// Never add a transition to an unreachable state.
if (dp[u] != INF) dp[v] = min(dp[v], dp[u] + cost);

Use half-open intervals [l,r) unless a problem forces another convention. They contain r-l items; empty intervals have l==r. Name whether an array is zero-based or one-based. A surprising number of “hard algorithm” bugs are indexing disagreements.

A progression you will repeat

Enumerate → find repeated work → retain a sufficient summary → prove it → implement → test. Do not skip the first step because it is slow. A brute-force model tells you exactly what the optimised algorithm must preserve.

Pause and solve: why is checking only adjacent scoreboard entries enough?

Coordinatewise ≤ is transitive. If every adjacent pair is nondecreasing, every earlier observation is ≤ every later one. Checking all pairs adds work without adding a constraint.

Your first milestone is to solve the three linked problems, explaining the invariant aloud before writing C++. Aim for a precise five-line proof, not speed.
