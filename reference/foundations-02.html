Greedy, sorting and search · Foundations

Proofs that make greedy choices trustworthy

Several requests give a start and finish time for using one room. You want to accept as many as possible without overlapping. If one reservation finishes earlier than another, when can you safely promise it a place? This question gives a concrete setting for proving a greedy choice.

The greedy trap

Suppose you want the maximum number of non-overlapping intervals. Taking the shortest interval sounds reasonable. Intervals [0,3), [3,6) and [2,4) disprove it: the shortest blocks the other two. The correct choice is the interval that finishes earliest.

The difference is a proof. Let G finish earliest and let O be the first interval in an optimum. Replace O by G. G finishes no later, so every later interval remains available. Repeat on the suffix. This is an exchange argument.

Four proof patterns to recognise

Exchange: replace part of an optimum with your choice without worsening the objective. This is the central tool for interval scheduling and sorted greedy assignments.

Stays ahead: after k decisions your partial solution has a resource at least as favourable as any competitor, such as an earlier finish time or more spare study time.

Lower bound plus construction: prove every answer costs at least L, then build one costing L. A radius-r circle needs square side at least 2r; the axis-aligned square achieves it.

Invariant: state what remains true after every update. DSU components represent exactly the connectivity introduced so far; a monotonic queue contains exactly the undominated candidates still in the window.

Marginal gains: a worked example

An attribute offers upgrade gains 12,3,3,3,…; another offers 8,5,5,5,…. With three upgrades, choose 12, 8, 5. Each sequence is nonincreasing, so choosing the largest available next gain is safe: any later gain from the same sequence requires all earlier ones and cannot be larger.

while (budget > 0) {
    auto item = heap.top(); heap.pop();
    if (item.isConstantTail) {
        answer += budget * item.gain;
        break;
    }
    answer += item.gain; --budget;
    heap.push(constantTailFor(item.attribute));
}

In BnPC, each attribute has at most one exceptional first gain. The batching above turns a budget-dependent loop into at most one special extraction per attribute. The proof gives the optimisation.

Convexity creates another exchange rule

Suppose block cost E(k) has increasing differences: E(k+1)-E(k) grows with k. If two block lengths differ by at least two, move one unit from the longer to the shorter. The cost cannot increase. Repeating makes all lengths differ by at most one. This is why the advanced solution to Crashing Competition Computer can enumerate the number of saves instead of all partitions.

Do not import this argument when the cost is concave: then unequal blocks may be better. Check the sign of the second difference explicitly.

How to challenge your own idea

Try ties, all-equal inputs, one huge item with many small ones, reversed order, negative values, and a case where a locally good choice consumes a rare resource. Random search against a brute-force oracle is excellent at finding counterexamples; it is not a replacement for a proof.

Checkpoint: is “take the highest value per weight” correct for 0/1 knapsack?

No. Capacity 4 with items (weight 3,value 5) and two items (weight 2,value 3) defeats it: ratio greedy takes value 5, while the two smaller items give 6. Fractional knapsack permits splitting items and has a different exchange argument.
